# TS Archive — архив видео с камер спецтехники (без S3)

Приложение принимает файлы MPEG-2 TS (~80 МБ, несколько минут записи каждый) с бортовых регистраторов техники на трубопроводе, индексирует их по времени и технике в PostgreSQL и показывает в веб-интерфейсе с таймлайном.

Видео хранится в одном экземпляре — в исходных `.ts`. Склеенных MP4 и TS нет: браузер воспроизводит исходные файлы по HLS-плейлисту с `EXT-X-BYTERANGE`. Плейлист собирается на лету из индекса ключевых кадров. Объектное хранилище не используется: архив лежит на обычной файловой системе (локальный диск, ZFS/XFS, NFS/CephFS), байты отдаёт Nginx по `X-Accel-Redirect` после проверки в API.

## Архитектура

```
 Регистраторы ──SFTP/rsync/SMB──►  /archive/incoming/{техника}/{камера}/YYYYMMDD_HHMMSS_mmm.ts
                                          │
 ┌────────────────────────────────────────┼─────────────────────────────────────────────┐
 │ worker-ingest (1 экз.)                 ▼                                             │
 │   ingest  — проверка «загрузка завершена», sha256-дедупликация, перенос в raw/,      │
 │             регистрация fragment (status=new); битые имена → quarantine/bad_name     │
 │   group   — группировка фрагментов камеры в сегменты по непрерывности                │
 │   cleanup — возврат зависших задач, удаление просроченных выгрузок и tmp             │
 ├──────────────────────────────────────────────────────────────────────────────────────┤
 │ worker-media (N экз., масштабируется)                                                │
 │   probe   — ffprobe: длительность, start_time, кодеки; индекс ключевых кадров        │
 │             (время → байтовое смещение PAT/PMT перед кадром), ~0,2 с на файл 80 МБ    │
 │   index   — шкала сегмента (offset каждого фрагмента), спрайт превью по ключевым      │
 │             кадрам; прокси H.264 только для MPEG-2 Video и других не-браузерных кодеков│
 ├──────────────────────────────────────────────────────────────────────────────────────┤
 │ worker-detect (образ с OpenVINO)                                                     │
 │   detect  — «человек в кадре»: FFmpeg декодирует исходные TS (DETECT_FPS кадр/с),    │
 │             YOLOX INT8 на CPU → интервалы в detection, рамки и миниатюры на диск      │
 │             + каски: детектор голов YOLOX-nano (в каске / без) → «без каски»          │
 └──────────────────────────────────────────────────────────────────────────────────────┘
            очереди = таблицы PostgreSQL (SELECT … FOR UPDATE SKIP LOCKED)
                                          │
              ┌───────────────────────────┴──────────────┐
              ▼                                          ▼
     PostgreSQL: vehicle, camera,               Файловая система /archive
     fragment (+ kf_t[], kf_pos[]), segment,    raw/ (единственная копия видео)
     event, detection, export, audit_log        thumbs/ proxies/ detections/ quarantine/ exports/ tmp/
              ▲                                          ▲ (read-only)
              │                                          │
         API (FastAPI)                          Nginx: статика UI, /api → API,
         /segments/{id}/playlist.m3u8  ──────►  /protected/ (internal) → /archive,
         /fragments/{id}/media → X-Accel        Range-запросы через sendfile
                                          ▲
                Браузер (hls.js из web/vendor): до 4 камер синхронно, таймлайн
```

Брокер сообщений не нужен: каждая стадия забирает задачи из PostgreSQL. Все стадии идемпотентны, состояние хранится в БД, упавший воркер не теряет работу (cleanup возвращает зависшие задачи).

## Воспроизведение без склейки

### Как это работает
1. На этапе `probe` ffprobe читает заголовки видеопакетов файла (без декодирования) и находит ключевые кадры. Для каждого кадра сохраняется время от начала файла и смещение ближайшего предшествующего PAT. Оба массива (`fragment.kf_t`, `fragment.kf_pos`) хранятся в БД. Для файла 160 с с GOP 2 с это 80 пар чисел, около 1,3 КБ.
2. Этап `index` считает шкалу сегмента: смещение каждого фрагмента равно сумме длительностей предыдущих. Длительность определяется по разнице PTS соседних файлов (`media.concat_durations`). Здесь же строится спрайт превью.
3. `GET /api/segments/{id}/playlist.m3u8` собирает VOD-плейлист. Каждый файл нарезается на куски около `HLS_CHUNK_SEC` секунд по ключевым кадрам:

```
#EXTM3U
#EXT-X-VERSION:4
#EXT-X-PLAYLIST-TYPE:VOD
#EXT-X-TARGETDURATION:7
#EXTINF:6.064000,
#EXT-X-BYTERANGE:1612100@0
/api/fragments/6/media
#EXTINF:6.000000,
#EXT-X-BYTERANGE:1612476@1612100
/api/fragments/6/media
...
#EXT-X-DISCONTINUITY           ← только если PTS соседних файлов не непрерывны (перезапуск регистратора)
#EXTINF:6.064000,
#EXT-X-BYTERANGE:1614356@0
/api/fragments/7/media
...
#EXT-X-ENDLIST
```

4. hls.js запрашивает `/api/fragments/{id}/media` с заголовком `Range`. API проверяет фрагмент и отвечает `X-Accel-Redirect`, а Nginx отдаёт нужные байты исходного файла через `sendfile` (`206 Partial Content`).

Каждый кусок начинается с PAT/PMT, поэтому перемотка возможна в любое место архива. Шкала плейлиста совпадает с картой фрагментов, и UI пересчитывает «позиция плеера ↔ время записи» так же точно, как раньше для MP4.

### Что проверено на тестовых данных
- Сегмент 320 с из двух файлов по 83 МБ: через плейлист декодируется 8000 кадров (25 fps), без ошибок декодера.
- Сегмент 120 с с перезапуском регистратора (PTS 6,3 → 1006,3): одна `#EXT-X-DISCONTINUITY`, 3000 кадров, в браузере воспроизведение проходит стык без остановки.
- В Chrome через hls.js 1.7.4: синхронный просмотр 3 камер (расхождение около 0,1 с), переход через стык файлов, автоматический перескок через разрыв записи, скорость до 16×, перемотка, прокси MPEG-2.
- Выгрузки из исходников: через разрыв записи (2 части) и через перезапуск регистратора (751 кадр за 30 с, без пропусков и дублей). Время ответа 0,1–0,7 с.

### Кодеки
| Видео в TS | Воспроизведение | Доп. место на диске |
|---|---|---|
| H.264 | напрямую из исходников (hls.js / Safari native HLS) | нет |
| HEVC | напрямую, если браузер декодирует HEVC (Safari, Chrome/Edge с аппаратной поддержкой). Иначе задайте `BROWSER_CODECS=h264`, и будет строиться прокси | нет / прокси |
| MPEG-2 Video и др. | прокси H.264 (`PROXY_TRANSCODE=auto`), `proxies/…/ID_HHMMSS.mp4` | прокси (CRF 26, зависит от сцены) |

Аудио: AAC и MP3 воспроизводятся. G.711 hls.js пропускает: видео идёт без звука, в выгрузках MP4 G.711 перекодируется в AAC. Звук в архиве при этом сохраняется без изменений.

## Разметка «человек в кадре»

Метки формируются заранее, отдельным этапом конвейера `detect`, а не во время просмотра: к моменту, когда оператор открывает запись, интервалы с людьми уже лежат в БД. По ним работают поиск по архиву, переходы и режим «только с людьми». Если открыть ещё не размеченный сегмент, он встаёт в начало очереди.

### Как работает
1. Сегмент проиндексирован (`status=done`) → `detect_status=pending`. Очередь: сначала открытые в интерфейсе и поставленные на пересчёт, потом новые записи, потом старый архив (дозаполнение после включения разметки идёт само).
2. FFmpeg читает исходные TS тем же списком ffconcat, что и превью, прореживает до `DETECT_FPS` (по умолчанию 2 кадр/с) и сразу вписывает кадр во вход модели (`scale` + `pad` = letterbox YOLOX). На диск ничего не пишется.
3. OpenVINO (`PERFORMANCE_HINT=THROUGHPUT`, асинхронная очередь запросов) прогоняет кадры через YOLOX. Перевод BGR uint8 → float32 NCHW встроен в граф модели, на Python остаются только NMS и склейка интервалов.
4. Срабатывания по кадрам склеиваются в интервалы: пауза до `DETECT_GAP_SEC` (3 с) не разрывает интервал, интервалы короче `DETECT_MIN_DUR_SEC` или из меньше чем `DETECT_MIN_HITS` кадров отбрасываются как шум.
5. Результат:
   - таблица `detection`: начало и конец (абсолютное время и позиция в сегменте), максимум людей одновременно, пиковая уверенность, зоны, миниатюра;
   - `detections/<техника>/<камера>/<день>/<сегмент>/boxes.json` — рамки по кадрам для наложения в плеере (≈7 КБ gzip на 8 минут с людьми) и `0001.jpg…` — лучший кадр интервала с рамками.

### Модель и лицензия
По умолчанию — YOLOX (Megvii, Apache-2.0): код и официальные веса можно использовать в закрытой корпоративной системе. Ultralytics YOLOv8/YOLO11/YOLO26 распространяются под AGPL-3.0 или платной Enterprise-лицензией; для закрытого внутреннего применения Ultralytics требует Enterprise. Этап `detect` принимает любую YOLOX-совместимую ONNX/IR-модель (`DETECT_MODEL`), в том числе дообученную на ваших кадрах.

| Модель | Вход | FP32, кадр/с | INT8, кадр/с | Когда брать |
|---|---|---|---|---|
| `yolox_tiny` | 416 | 26,3 | — | много камер, люди крупно (кабина, ближняя зона) |
| `yolox_s` | 640 | 6,9 | 15,1 | основной вариант: дальние фигуры у траншеи, у стрелы |
| `yolox_m` | 640 | — | — | если `s` пропускает людей вдали; примерно в 2,5 раза тяжелее `s` |

Замер — только инференс, 2 vCPU Xeon (Ice Lake, AVX-512 VNNI) в тестовой среде. На тестовых изображениях INT8 нашёл тех же людей с той же уверенностью (±0,02), что и FP32.

### Производительность на Xeon Gold 5320 (16 vCPU)
Gold 5320 — Ice Lake-SP с AVX-512 и DL Boost (VNNI), поэтому INT8 через OpenVINO даёт на нём основной выигрыш.

Замер полного этапа в тестовой среде (2 vCPU): сегмент 8 мин 720p25 H.264, 2 кадр/с, YOLOX-s INT8 — 960 кадров за 92 с, то есть ×5,2 реального времени. На остальных тестовых сегментах (H.264, MPEG-2 Video, сброс PTS) — ×4,2–4,8, около 8,5 кадр/с. Из них декодирование H.264 — около 28 с, остальное — инференс.

Ориентир для 16 vCPU (линейная экстраполяция, проверьте на своих данных):

| Параметры | Камер в реальном времени | Дозаполнение архива |
|---|---|---|
| YOLOX-s INT8, 2 кадр/с, `DETECT_CPUS=12` | ≈ 25–30 | сутки записи одной камеры ≈ 45–60 мин |
| YOLOX-s INT8, 1 кадр/с | ≈ 50 | вдвое быстрее |
| YOLOX-tiny, 2 кадр/с | ≈ 60+ | — |

Рекомендуемая настройка для 16 vCPU: один контейнер `worker-detect`, `DETECT_CPUS=12`, `DETECT_THREADS=12`, YOLOX-s INT8, 2 кадр/с; остальные 4 vCPU — PostgreSQL, API, Nginx, ingest и media. Несколько контейнеров detect не ускорят работу: OpenVINO в режиме THROUGHPUT сам загружает все выделенные ядра. Если виртуальные CPU — потоки Hyper-Threading, а не физические ядра, реальная производительность будет ближе к нижней границе оценки.

Фактическая скорость пишется в лог (`×N реального времени`) и в `/api/stats` → `detect.realtime_factor_24h`: это число камер, которые этап успевает размечать в реальном времени.

### Установка
```bash
sh tools/get_models.sh                      # ./models/yolox_s.onnx, yolox_tiny.onnx (≈56 МБ)
docker compose build worker-detect
docker compose up -d worker-detect          # сначала можно с FP32: DETECT_MODEL=/models/yolox_s.onnx
# когда в архиве есть готовые сегменты — INT8 на ваших кадрах (2–3 мин):
docker compose run --rm worker-detect quantize /models/yolox_s.onnx /models/yolox_s_int8.xml 300
# в .env: DETECT_MODEL=/models/yolox_s_int8.xml
docker compose up -d worker-detect
docker compose exec api python -m tsarchive detect all      # пересчитать архив новой моделью
```
Каталог `./models` должен быть доступен на запись uid 1000 (для `quantize`). В изолированной сети: `MODELS_URL=http://nexus.local/repository/raw/yolox sh tools/get_models.sh`, образ — с `--build-arg PIP_INDEX_URL=…` и `--target detect`.

### Зоны и исключения камеры
Координаты — доли кадра (0..1), многоугольники. `ignore` — люди с центром рамки внутри не учитываются (например, оператор в кабине или отражение в стекле). `zones` — именованные зоны: человек считается в зоне, если низ рамки (ноги) внутри. Такие интервалы помечаются красным, их можно искать отдельно.
```bash
curl -X PUT http://host:8080/api/cameras/5/detect-config -H 'Content-Type: application/json' -d '{
  "ignore": [[[0,0.55],[0.35,0.55],[0.35,1],[0,1]]],
  "zones": {"Под стрелой": [[0.55,0.45],[1,0.45],[1,1],[0.55,1]]},
  "min_conf": 0.5, "requeue": true}'
```
`"enabled": false` отключает разметку камеры. `requeue: true` пересчитывает её архив с новыми правилами.

### Ограничения разметки
- Рамки в плеере берутся с ближайшего размеченного кадра (шаг 1/`DETECT_FPS`): у быстро идущего человека рамка может отставать на долю секунды. На интервалы и поиск это не влияет.
- При 2 кадр/с человек, промелькнувший в кадре меньше чем на 0,5–1 с, может не попасть в интервалы. Для таких камер поднимите `DETECT_FPS` до 4–5 (нагрузка растёт линейно).
- Готовые веса обучены на COCO. Ночная ИК-картинка, пыль, сильные блики, люди частично закрыты техникой или видны только сверху — на таких кадрах возможны пропуски. Лечится порогами и зонами камеры, а при необходимости дообучением на кадрах архива.

## Проверка касок

Метка `no_helmet` («без каски») ставится на интервалы, где в кадре есть человек без каски. Работает в том же проходе разметки, видео второй раз не декодируется.

### Как работает (режим `heads`, по умолчанию)
1. YOLOX-s находит людей (см. выше).
2. На том же кадре (вписан во вход 640×640) детектор голов YOLOX-nano (`models/heads_nano.onnx`, 3,6 МБ, обучен `tools/train_heads.py`) находит головы двух классов: `helmet` (в каске) и `head` (без каски). Одна голова не может получить оба класса (NMS без учёта класса).
3. Головы сопоставляются с рамками людей (`heads.associate`: центр головы — в верхней части рамки).
   - Если в одной рамке несколько голов (люди стоят вплотную и YOLOX выдал общую рамку), людей считается по числу голов.
   - Голова без рамки человека с уверенностью ≥ `HEADS_ALONE_CONF` считается отдельным человеком (виден только по голове и плечам).
4. Головы «без каски» с уверенностью ≥ `HEADS_NO_CONF` склеиваются в интервалы `no_helmet` (минимум `HELMET_MIN_HITS` кадров). Число людей в интервале «люди» учитывает лишние головы.
5. `boxes.json` v3: кадр = `[t, рамки людей, головы, людей в кадре, без каски]`, голова = `[x1, y1, x2, y2, уверенность, код (1 в каске / 2 без), индекс рамки человека или -1]`.

Почему не квадрат головы из рамки человека (прежняя схема, осталась как `HELMET_MODE=crop`): если люди стоят вплотную, рамка общая или закрытый человек не найден вовсе, а вычисленный квадрат попадает между головами. Пример — PT-104/cam6 20.11.2026 08:33:46 МСК: трое, YOLOX нашёл двоих (у заднего видны только каска и лицо, уверенность 0,10), классификатор квадрата не определил человека без каски. Детектор голов находит все три головы (каска 0,83, каска 0,52, без каски 0,76).

В интерфейсе: рамки людей — тонкие оранжевые, рамки голов — зелёная «каска N%» / пурпурная «без каски N%», значок «Людей в кадре: N · без каски: K». Переключатель «все люди / без каски» меняет навигацию ◀ ▶, режим «только без каски» и список слева. API: `/api/detections?label=no_helmet`, метрика `tsarchive_detections{label="no_helmet"}`.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `HELMET_MODE` | `auto` | `heads` / `crop` / `off`; `auto` — `heads`, если есть модель, иначе `crop` |
| `HEADS_MODEL` | `/models/heads_nano.onnx` | детектор голов (вход должен совпадать с детектором людей, 640×640) |
| `HEADS_CONF` | 0,4 | голова «в каске» учитывается от этой уверенности |
| `HEADS_NO_CONF` | 0,5 | голова «без каски» — от этой уверенности |
| `HEADS_ALONE_CONF` | 0,5 | голова без рамки человека считается человеком |
| `HEADS_MIN_PX` | 6 | сторона головы во входе модели (640), минимум |
| `HEADS_ALL_FRAMES` | 1 | искать головы и в кадрах, где YOLOX людей не нашёл |

Отключить для камеры: `PUT /api/cameras/{id}/detect-config` с `{"helmet": false}`.

| 20–50 | 2 + 0 | 2,05 | 57 | нет — верно |
| 145–175 | 0 + 3 | 2,98 | 57 | 145–175, до 3 — верно |
| 220–250 | 2 + 1 | 3,00 | 60 | 220–250, 1 — верно (раньше пропуск) |
| 290–320 | 2 + 0 | 1,07 | 4 | нет — верно; YOLOX людей не видит, головы 0,4–0,5 |
| 360–390 | 0 + 4 | 4,00 | 60 | 360–390, 4 — верно |
| 430–460 | 1 + 2 | 2,03 | 2 | пропуск: у одного каска в руке у головы, второй — отражение; мужчину в каске модель считает «без каски» 0,59 |

Ложных «без каски» вне сцен — 0. «Каска» 0,4–0,5 на цветных блоках testsrc2 — в 34 кадрах (людьми не считаются, порог `HEADS_ALONE_CONF`). Было с прежней схемой: найдено 2 сцены из 4.

Скорость: сегмент 480 с — 122 с на 2 vCPU (×4 реального времени), столько же, сколько только люди со схемой `crop`: второй поток FFmpeg в исходном разрешении больше не нужен. Детектор голов — ≈ 50 мс на кадр (замер на 2 vCPU), идёт параллельно с асинхронным детектором людей.

### Дообучение на своём архиве (рекомендуется)
```bash
pip install -r requirements-detect.txt torch torchvision onnx
python tools/get_hardhat.py --out /data/hardhat
curl -LO https://github.com/Megvii-BaseDetection/YOLOX/releases/download/0.1.1rc0/yolox_nano.pth
# кадры с людьми + предразметка голов текущей моделью (COCO)
python -m tsarchive head-frames 6 /data/my_heads 500
# импорт /data/my_heads в CVAT как «COCO 1.0», исправить рамки helmet/head, экспорт обратно в COCO
python tools/train_heads.py --data /data/hardhat --extra /data/my_heads/coco.json \
    --resume models/heads_nano.pt --epochs 6 --iters 150 --out models/heads_nano.onnx
```
Хватает 300–500 кадров с каждого типа камеры (день, ночь/ИК, вид сверху, дальний план). С нуля: `--weights yolox_nano.pth --epochs 12 --iters 150`. На Xeon Gold 5320 (16 vCPU) ожидаемо в 5–8 раз быстрее, чем 66 мин на 2 vCPU (оценка, не замер). После замены файла модели воркер подхватит её после перезапуска; пересчитать архив — `detect-config` с `requeue: true`. Метрики модели пишутся в `models/heads_nano.json`.

Схема `crop` (классификатор `models/helmet_cls.onnx`, `tools/train_helmet.py`, `helmet-crops`) оставлена как запасная: `HELMET_MODE=crop`.

### Ограничения
- Голова меньше ~6 px во входе 640 (≈12 px в кадре 1280×720) не находится. Для дальних планов камеры поднимите разрешение входа (переобучение с `--export-img 960` вместе с детектором людей) или используйте зоны.
- Каска в руке у головы, капюшон, шапка, вид строго сверху, отражения — возможны ошибки класса (см. сцену 430–460). Пороги `HEADS_*` подбирайте по своей разметке.
- Метка — подсказка оператору, а не основание для взыскания без просмотра.

## Расчёт на файлы ~80 МБ

| Параметр | Значение | Почему |
|---|---|---|
| Длительность файла | ~2–5 мин (80 МБ при 2–5 Мбит/с) | время берётся из имени, длительность — из ffprobe |
| `SEGMENT_MAX_SEC` | 3600 | сегмент — час записи ≈ 15–30 файлов, плейлист ≈ 600 кусков (~60 КБ, gzip) |
| `IDLE_CLOSE_SEC` | 600, но не меньше 2× длительности файла | следующий файл приходит через несколько минут, сегмент не рвётся |
| `INGEST_STABLE_SECONDS` | 30 | 80 МБ по медленному каналу пишутся долго; лучше загружать как `.part` и переименовывать |
| `HLS_CHUNK_SEC` | 6 | кусок ≈ 3 МБ при 4 Мбит/с: быстрый старт и перемотка, немного запросов |
| Превью | ключевые кадры (`-skip_frame nokey`), раз в 15 с | 5 мин записи 720p — 0,75 с |
| Чтение оригиналов | потоковое, по 4 МБ | sha256, извлечение и проверка не держат файл в памяти |

**Объём диска ≈ 1× входящего потока** плюс превью (около 0,05 %) и прокси только для не-браузерных кодеков. Пример: 50 камер × 4 Мбит/с × 10 ч/сут ≈ 0,9 ТБ/сут. Вариант со склеенными MP4 потребовал бы около 1,8 ТБ/сут.

Нагрузка на чтение: каждая камера на 1× — один Range-запрос на ~3 МБ раз в 6 с. На 16× — около 2–3 запросов в секунду (~8 МБ/с на камеру 4 Мбит/с). Сеть между Nginx и браузером должна это выдерживать.

## Ключевые решения

### Точная шкала без рывков на стыках
Регистратор режет один непрерывный поток, поэтому PTS соседних файлов непрерывны. Длительность файла на шкале берётся как разница `start_time` соседних файлов (`media.concat_durations`). Длительность видеопотока для этого не годится: из-за аудиокадров AAC она «дрожит», и на стыках появляются дубли или пропуски кадров. Учитываются переполнение 33-битного PTS и проверка правдоподобия. Если регистратор перезапускался, берётся длительность видео, а в плейлист ставится `DISCONTINUITY`.

Та же шкала используется в ffconcat-списках: для превью, выгрузок и прокси.

### Правила закрытия сегмента
Сегмент закрывается, когда выполняется любое из условий:
- разрыв между концом предыдущего и началом следующего фрагмента больше `GAP_THRESHOLD_SEC`;
- фрагменты перекрываются больше чем на `OVERLAP_TOLERANCE_SEC`;
- изменилась сигнатура потоков (кодек, разрешение, pix_fmt, аудио);
- длина достигла `SEGMENT_MAX_SEC`;
- от камеры нет новых фрагментов дольше `IDLE_CLOSE_SEC`.

Группировка не заходит дальше первого ещё не проанализированного фрагмента камеры, поэтому отставание probe не рвёт сегменты.

### Сохранность оригиналов
- Исходные `.ts` не изменяются, не перепаковываются и не перемещаются после приёма. Это единственная копия видео и одновременно источник воспроизведения.
- Для каждого файла хранится sha256, дубликаты по содержимому отбрасываются.
- `python -m tsarchive verify 1000` выборочно сверяет sha256.
- `GET /api/fragments/{id}/download` и `python -m tsarchive extract` отдают оригинал байт в байт.

## Веб-интерфейс
- Дерево: участок трубопровода → техника → камеры. Клик по технике открывает все её камеры (до 4) синхронно.
- Таймлайн: дорожка на камеру. Зелёный — запись, жёлтый — обработка, красный — ошибка, фиолетовые штрихи — метки.
  - Колесо мыши масштабирует от 30 с до 90 дней, перетаскивание сдвигает, клик переходит к моменту, Shift+протягивание выделяет интервал для выгрузки.
  - При наведении показывается превью кадра и сведения о сегменте.
- Воспроизведение 0,5–16×. Буфер hls.js растёт со скоростью (20 с × скорость, до 120 с). Разрывы записи пропускаются автоматически, камеры подтягиваются к ведущей, если расходятся больше чем на 1 с.
- Люди: под полосой записи каждой камеры — полоса «люди» (оранжевый; красный — человек в зоне камеры; тонкий серый штрих — сегмент ещё размечается). При наведении — миниатюра и число людей. Кнопки «◀ люди / люди ▶» (клавиши P / Shift+P), флажок «только с людьми» пропускает при воспроизведении всё, где людей нет, флажок «рамки» включает рамки поверх видео и счётчик «Людей в кадре». Слева — список интервалов видимого диапазона с миниатюрами, клик переходит к началу.
- Каски: интервалы, где кто-то без каски, — пурпурные поверх полосы «люди». Переключатель «все люди / без каски» задаёт, по каким интервалам работают кнопки перехода, список слева и режим «только без каски». Рамки: зелёная — в каске, пурпурная — без каски (с вероятностью), оранжевая — не определить (голова мала или не видна); счётчик «Людей в кадре: N · без каски: K».
- Клавиши: пробел — пуск/пауза, ←/→ — ±10 с (с Shift — ±60 с), +/− — масштаб, P / Shift+P — следующий / предыдущий интервал с людьми.
- Браузеры: всё с MediaSource Extensions через hls.js (Chrome, Edge, Firefox, Яндекс Браузер), Safari — нативный HLS. Проверено в Chrome.

## Эксплуатация

```bash
docker compose up -d --scale worker-media=4        # больше параллельных probe/индексаций
docker compose exec api python -m tsarchive reindex 123
docker compose exec api python -m tsarchive extract 456 /archive/tmp/frag.ts
docker compose exec api python -m tsarchive verify 1000
docker compose exec api python -m tsarchive detect cam 5     # пересчитать разметку камеры (seg <id> | all)
```

- Файловая система: XFS или ZFS (`recordsize=1M` для dataset с видео). `incoming/` и `raw/` должны быть на одной ФС — тогда перенос файлов мгновенный (rename), без копирования 80 МБ.
- Неизменяемость: отдельный dataset ZFS для `raw/` с регулярными снапшотами (`zfs snapshot`), либо `chattr +i` на принятые файлы.
- Резервные копии: `pg_dump` или `pgBackRest` для БД (в ней индекс ключевых кадров и шкала); `zfs send`, `restic` или `rsync` для `raw/`. Превью, прокси и `detections/` можно не бэкапить: `reindex` и `detect` строят их заново. Индекс ключевых кадров восстанавливается повторным приёмом файлов.
- Масштаб: при одном хосте все контейнеры используют общий каталог. При нескольких хостах `/archive` монтируется по NFS или CephFS на воркеры, API и Nginx (в Kubernetes — RWX PVC). Nginx читает с диска только запрошенные диапазоны.
- Мониторинг: `/metrics` (очередь, задержка конвейера, объём, свободное место), ошибки сегментов — в `/api/stats` и логах воркеров.

## Ограничения
- Выгрузка начинается с ближайшего предыдущего ключевого кадра, поэтому граница может сдвинуться на длину GOP.
- Время берётся из имени файла. Если часы регистратора уходят, исправлять нужно на стороне выгрузки (или задать смещение при переименовании).
- Регистратор должен записывать PAT/PMT периодически: так делает большинство устройств и FFmpeg. Если PAT перед ключевым кадром не найден в пределах `PAT_SEARCH_BYTES`, кусок начинается с самого кадра. При последовательном просмотре это работает, но первая перемотка в середину такого файла может не стартовать.
- HEVC воспроизводится только там, где браузер его декодирует.
